What model size and architecture do to a GPU and a rack

Dense models from 1B to 405B parameters, mixture-of-experts from 3B to 37B active, four attention designs, Mamba-2 and a hybrid, contexts to 128k, on HGX A100, HGX H100, HGX B300 and GB300 NVL72. Every point is a simulated decode step, prefill or training step: each distinct kernel runs at cycle level on the SM model, every collective runs on the simulated NVLink fabric, and the step is split into what it was waiting on.

Findings

Decode is a memory problem at every size

79% of decode points

are HBM-bound across 1B to 405B and all four systems (292 simulated decode steps). None of them reaches compute-bound, even at batch 256: weights and KV cache are re-read every step, and padded M=16..256 tiles leave the tensor cores mostly idle.

Bigger models cost per token about in proportion to their weights

61x

more tokens/s per GPU for llama3.2-1b (14.5k, 1gpu b256) than llama3-405b (240, tp8 b64) on GB300 NVL72 at 20 tokens/s per user. The best layout moves from one GPU per replica to TP8 as the model grows: llama3.2-1b 1gpu, llama3-8b tp2, llama3-70b tp4, llama3-405b tp8.

Small models are bound by everything except the GPU's peak

35% of the step

of a Llama-3.2-1B batch-1 decode on B300 is launch gaps and latency-bound kernels (958 µs per token). The fix is in the serving stack (graphs, fusion, a megakernel), not in a bigger GPU; see the launch-mode chart.

Prefill and training are compute problems

71% of prefills

are compute-bound (8k-token prompts). Training MFU on HGX B300 at the best layout: llama3.2-1b 48% (dp8), llama3.2-3b 50% (dp8), llama3-8b 51% (dp8), qwen2.5-32b 49% (dp8), llama3-70b 47% (tp2xdp4). On GB300 NVL72, Llama-3-405B trains best at tp8xdp9 (46% MFU); adding pipeline stages brings tp8xpp3xdp3 down to 34% as communication grows from 13% to 34% of the step (rack-scale training points extrapolated from 6- and 12-layer runs).

Three generations: compute grew faster than bandwidth

10x prefill, 8x decode

per GPU for llama3-70b, HGX B300 over HGX A100 (best layouts, decode at 20 tokens/s per user). Prefill tracks the 8x tensor peak; decode tracks the 4x HBM bandwidth plus B300's 288 GB, which allows larger batches per GPU. The A100 GEMM model is pessimistic, so read the A100 side as a lower bound.

At long context, the KV layout decides the batch

4x

tokens/s per GPU for MLA over GQA-4 at 128k context on one B300, each at the largest batch that fits: MHA 73 (batch 1), GQA-4 168 (batch 1), MQA 2.5k (batch 64), MLA 662 (batch 16). Per token the cache is 512 KB, 128 KB, 16 KB and 36 KB. MQA wins on bytes; MLA keeps per-head quality but its 576-wide decode attention spends more time in the tensor pipe.

Mamba-2 does not care how long the context is

41x

tokens/s per GPU for Mamba-2 over GQA at 128k context (6.9k vs 168). GQA loses 25x from 8k to 128k because its batch must shrink to fit the cache; Mamba-2's state is the same size at every context, and the hybrid with 4 attention layers keeps 2.2k.

DeepSeek-V3 wants expert parallelism

EP32

is the best DeepSeek-V3 layout on GB300 NVL72 at batch 128 per rank: 4.7k tokens/s per GPU, 10x the best tensor-parallel layout (tp8, 488). Under EP each GPU keeps a few whole experts and serves its own batch, so the expert weights it streams are shared by many more tokens. Past ep32 the gain is flat (ep72: 4.7k); all-to-all is 16% of the step.

Two-micro-batch overlap rarely pays on NVLink

wins 0 of 30

EP layouts at batch 128. Each half-batch re-reads every weight, which costs more than the all-to-all it hides: on NVLink5 the all-to-all is at most 19% of these steps, so there is little to hide. Across racks over InfiniBand, with a slower all-to-all, the balance may differ (not simulated here).

At 128k, a 70B model spends its step reading KV

62% attention

of Llama-3-70B's TP8 decode step at 128k context and batch 16 on GB300 NVL72, against 11% at 4k. Throughput falls 2.3x; the Mamba-2 hybrid of the same size keeps 2.4x more tokens/s per GPU. Batch 64 at 128k does not fit at all: 361 GB per GPU.

Launch overhead is a model-size effect

1.61x

from eager launches (1226 µs) to no gaps at all (763 µs) for Llama-3.2-1B at batch 1 on B300; CUDA graphs get 862 µs. For Llama-3-70B at TP8 the same change is 1.32x. The measured Hazy megakernel does 608 µs per token, so fusion is worth more than removing gaps.

A prefill chunk is a tax on every decoding user

+228% TPOT

when a 2048-token prompt chunk joins a 64-sequence Llama-3-8B decode batch on B300 (9.3 → 30.4 ms). The step turns from HBM-bound to compute-bound once the chunk passes a few hundred tokens, which is where chunk size should stop.

FP8 helps decode through bytes and prefill through FLOPs

1.08–2.19x

from BF16 to FP8 GEMMs on B300 across 8B, 70B and 405B. Attention stays BF16, so decode at 8k context gains less than the halved weight bytes suggest.

Use it as a tool

Everything on this page comes from two commands. rackscale plan answers one question with a machine-readable result, so a script or an agent can call it in a loop: change a model dimension, a system or a target and read back the best layout and what bounds it.

# best layout for Qwen3-235B decode on an NVL72 at 30 tokens/s per user, as JSON
rackscale plan qwen3-235b-a22b --system gb300 --context 8192 --min-tps-user 30 --json

# a custom grid, or one of this page's studies
rackscale sweep --models llama3-8b,llama3-8b-mla --systems b300 --contexts 8192,131072 --batches 1,64
rackscale sweep --study moe --jobs 8 -o moe.json

# rebuild this page
python research/model_sweep/run.py && python research/model_sweep/build_page.py

The same is available from Python as rackscale.sweep (best_plan, run, study_points, pareto), and to agents as the best_layout tool of the rackscale MCP server (claude mcp add rackscale -- rackscale-mcp), next to simulate, find_bottlenecks and what_if.

How to read these numbers

A kernel counts as compute-bound when its tensor pipe runs at half of peak or more, HBM-bound when it moves HBM bytes at half the achievable bandwidth or more, and latency-bound when it reaches neither (too few CTAs, wave tails, dependency chains, barriers). Comm is collective time not hidden behind kernels and launch is the GPU sitting idle between kernels. Throughput assumes every replica of a layout matches the simulated one, which holds for TP and for EP under balanced routing.
